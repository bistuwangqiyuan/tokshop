## 一、模型与硬件

### S-01 Kimi K3 模型规格

来源：MoonshotAI 官方仓库 <https://github.com/MoonshotAI/Kimi-K3>（仓库创建于 2026-07-27T08:01:37Z）

| 项 | 值 |
| --- | --- |
| Architecture | Mixture-of-Experts (MoE) |
| Total Parameters | 2.8T |
| Activated Parameters | 104B |
| Number of Layers | 93（1 dense + 69 KDA + 24 Gated MLA） |
| Latent MoE Dimension | 3584 |
| MoE Hidden Dimension (per Expert) | 3072 |
| Number of Experts | 896 |
| Selected Experts per Token | 16 |
| Number of Shared Experts | 2 |
| Context Length | 1,048,576 |
| Quantization | MXFP4 weights / MXFP8 activations（quantization-aware training） |

**关键性**：`MXFP4 weights` 是量化感知训练的原生权重格式，不是事后压缩。这是单机装下 2.8T 模型的前提。

**本报告的一处克制**：由 latent MoE 维 3584、每专家隐层 3072、896 专家推算的参数量与官方 2.8T 总量、104B 激活量无法自洽（推算的每专家参数量会使总量超出 2.8T，或使激活量超出 104B）。这说明 "Stable LatentMoE" 的参数共享方式未完全公开。因此模型**只用 16/896 这两个官方数字计算专家覆盖率 φ(B)，不反推专家权重占比**。

## 二、产能实测

### S-06 吞吐实测（一）：并发扫描

来源：Openzeka 白皮书《Kimi K3 Inference Benchmark on DGX-B300》<https://whitepapers.openzeka.com/papers/kimi-k3-dgx-b300-inference-benchmark/>（2026 年 7 月）

测试条件：DGX-B300（8×GPU）、TP8、KV Cache FP8、`--gpu-memory-utilization 0.95`、`--max-model-len 1048576`、启用前缀缓存。

聚合输出吞吐（tok/s）：

| 并发 c | vLLM 直出 | vLLM+投机 | SGLang 直出 | SGLang+投机 |
| --- | --- | --- | --- | --- |
| 1 | 101 | 188 | 83 | 130 |
| 4 | 293 | 398 | 237 | 228 |
| 16 | 703 | 698 | 697 | 355 |
| 32 | 1126 | 740 | 1074 | 493 |
| 64 | **1759** | 717 | **1863** | 931 |

c=64 时延迟：vLLM 直出 TTFT 均值 **731.7 ms**、P90 **1107.0 ms**、ITL 30.8 ms、单用户 27.5 tok/s。

SLO 阈值原文：TTFT ≤ 1000 ms（Nielsen 的 1 秒"思维流"界限）、TPS ≥ 15 tok/s。

**取用**：短上下文标定点取 vLLM 直出 c=64 的 **1,759 tok/s**（未取 SGLang 的 1,863，保守）。TTFT 均值与 P90 用于选址的 SLO 判断。

**投机解码的结论**：break-even 约 c=16（vLLM）与 c=4（SGLang），高负载下为净损失。生产高负载应关闭。

### S-07 吞吐实测（二）：长上下文与显存分配

来源：GPUStack《Day 0 Support for Kimi-K3: vLLM vs. SGLang Inference Benchmark on 8×B300 GPUs》<https://dev.to/gpustack/gpustack-day-0-support-for-kimi-k3-vllm-vs-sglang-inference-benchmark-on-8xb300-gpus-2g0g>

测试条件：单节点 8×B300；每 GPU 可见显存 **267.69 GiB**；Kimi-K3 (MXFP4)；输入 64K/200K；输出 3K；并发 10；随机数据集。

| 场景 | vLLM | SGLang |
| --- | --- | --- |
| 64K 稳态解码吞吐 | **~501 tok/s** | ~335 tok/s |
| 200K 稳态解码吞吐 | ~163 tok/s | **~268 tok/s** |
| 64K 端到端耗时 | 100.5 s | 150.8 s |
| 200K 端到端耗时 | 295.2 s | 225.3 s |

vLLM 显存分配（每 GPU）：模型权重与非 torch 内存 197.72 GiB、峰值激活 12.82 GiB、CUDA Graph 5.13 GiB、**KV Cache 43.76 GiB**。**KV 池容量 2,687,776 token**。

引擎日志自报稳态聚合 **prefill 吞吐约 19K–23K tok/s**。

冷启动：权重加载 163.8 s、CUDA Graph 捕获 85–88 s、引擎初始化 409.61 s、**容器到就绪约 10.6 分钟**。

**预填速率的反解**（本报告的推导，非原文数字）：

- 64K 组：10 × 65,536 输入；e2e 100.5 s；解码 10×3000 @501 tok/s = 59.88 s ⇒ 预填 40.62 s ⇒ **16,134 tok/s**
- 200K 组：10 × 204,800 输入；e2e 295.2 s；解码 10×3000 @163 tok/s = 184.05 s ⇒ 预填 111.15 s ⇒ **18,425 tok/s**

两次独立反解落在同一量级，取较低者，保守。该速率对应 MFU 仅 2.80%，偏低但符合 MoE 长上下文预填特征。

### S-22 OpenRouter 的 provider 结算机制

来源：<https://openrouter.ai/docs/guides/get-started/for-providers>、<https://openrouter.ai/providers/apply>、<https://openrouter.ai/docs/faq.md>、<https://openrouter.ai/pricing>

- **不对 provider 价格加价**："We pass through the pricing of the underlying providers; there is no markup on inference pricing"。平台向终端用户收取 5.5% 的充值手续费，与 provider 无关。
- provider **自设美元价**，通过 `/models` 端点发布定价、上下文长度、最大输出、数据中心位置。
- 结算方式：**按月开票**（monthly invoicing），token 计数自动对账。
- 技术门槛：`/chat/completions` 须 OpenAI 兼容、支持流式、流式与非流式都要返回 usage。
- 路由：默认按价格负载均衡并考虑可用率；可按 `price` / `throughput` / `latency` 排序。
- **Auto Exacto 会对统计离群的 provider derank**，依据吞吐、工具调用遥测与基准分三路信号；**新 provider 先落在中间层**直到积累足够流量。

**关键性**：这条决定了本模型的双轨费率结构（聚合渠道无手续费但有账期，自建渠道有手续费但预付），也决定了 SLO 看门狗的必要性。

### S-25 各市场空置率与马来西亚电价

来源：TNGlobal（2026-07-31）<https://technode.global/2026/07/31/singapore-tightens-data-center-growth-as-johor-bangkok-jakarta-race-ahead/>

> Johor's colocation vacancy rate stands at just **0.7 percent**, compared with **4.9 percent** in Singapore, **20.5 percent** in Jakarta and **23.3 percent** in Bangkok.

**本报告的反解**：
